id: ADR_006
title: ADR-006 - Explicit Terraform Resource Providers and Enhanced Preflight Validation
description: Use explicit Resource Provider registration and Enhanced Validation during the AzureRM v5 upgrade. Enable new Preflight Validation for supported resources.
---

- **Status:** Accepted
- **Decision Date:** 2026-10-21
- **Deciders:** PEACH Design Team, Lead Solution Architect
- **Category:** Infrastructure, Deployment

## Context

PEACH is upgrading the AzureRM provider from v4 to v5. In v4, the provider checked and
registered a broad set of Azure Resource Providers (RPs) by default. In v5, it registers none by default. Without
another registration arrangement, an unregistered RP could prevent a deployment.

V5 also disables location and RP Enhanced Validation by default and offers opt-in Preflight Validation for supported
resources. We need to choose which RPs Terraform should register and which checks should run during planning.

## Decision

PEACH will explicitly register the RPs used by each Terraform root (core and instance) rather than restore the broad
legacy set. We will enable Enhanced Validation for locations and RPs and opt in to Preflight Validation for supported
resources. When a supported resource's location is not yet known at plan time, Preflight Validation will use Canada
Central as its fallback location.

The exact lists and settings are in the
[core provider configuration](../../infra/core/providers.tf) and
[instance provider configuration](../../infra/instance/providers.tf).

## Rationale

Explicit lists keep Terraform from checking and potentially registering the broad legacy RP set. They also document
which Azure services PEACH uses. Enabling location and RP Enhanced Validation retains earlier feedback for some invalid
resource arguments. Preflight Validation sends supported resource payloads to the Azure Deployments Validation API at
plan time, where it may catch errors such as Azure Policy violations before apply.

> [!NOTE]
> These are checks, not guarantees. In particular, Enhanced Validation does not reliably reject a misspelled RP in the
> registration list (as of now), and Preflight Validation does not check every resource, dependency, quota, or computed
> value. A no-change plan does not exercise Preflight Validation of a resource creation or update.

### Assumptions

- Deployment identities have permission to register the listed RPs, or the RPs are already registered in each target
  subscription.
- Azure credentials are available for the API calls made during plan.

## Options Considered

- **V5 defaults:** Do not register RPs automatically or perform Enhanced Validation. This requires separate RP
  registration and moves validation and pre-flight errors to the apply stage.
- **Legacy registration:** Preserve broad v4 RP registration and Enhanced Validation, including services PEACH does not
  use.
- **Explicit list with Enhanced Validation (chosen):** Register only PEACH's required RPs and enable available
  plan-time checks, accepting the added API calls and limited coverage.

## Consequences

### Positive

- Terraform checks a smaller, documented set of RPs for registration.
- RP registration is explicit and clear.
- Some invalid locations and supported resource payloads can be rejected during plan rather than apply.

### Negative

- New Azure services require updates to the RP lists.
- Enhanced Validation and Preflight Validation make additional API calls during plan and require Azure credentials.
  Preflight is best-effort and cannot guarantee that an apply will succeed.
