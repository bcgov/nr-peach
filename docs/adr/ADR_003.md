- **Status:** Accepted
- **Decision Date:** 2026-02-09
- **Deciders:** PEACH Design Team
- **Category:** Security, Access Management

## Context

As the data stored in NR-PEACH has a Protected B classification, access to permitting resources must be controlled and
gated to only known and authorized service accounts. In addition, we also have a need to ensure that there are certain
service accounts that are only allowed to write and update to certain specific records within the system that they are
custodians for. While there are multiple ways of achieving this kind of role based access management, we need to select
and follow a well known security standard in order to mitigate all reasonable security risks from this platform.

## Decision

We will be using standard OIDC Authentication flows with Keycloak service accounts to obtain JWTs for secure access in
NR-PEACH. All service accounts must present a valid JWT token to the system prior to getting access to any resources.
In addition, all service accounts will be assigned specific scopes which will assert which systems they are allowed to
represent and modify within NR-PEACH. These scopes will align with the
[CSNR IT Service Management](https://apps.nrs.gov.bc.ca/int/jira/secure/ObjectSchema.jspa?id=1&typeId=5) values and be
included in the JWT claims. Each network transaction shall be validated by the system for the presence of appropriate
scopes within each request when modifying data.

## Rationale

Using a well known OIDC authentication flow with Keycloak service accounts ensures that NR-PEACH benefits from a
standardized, secure, and widely adopted method for obtaining and validating JWTs. This approach leverages existing
security infrastructure, reduces the risk of custom implementation errors, and provides a clear mechanism for enforcing
fine-grained access control based on scopes.

### Assumptions

- The system assumes that all service accounts will be properly registered and managed within Keycloak.
- Service accounts will be assigned appropriate scopes that align with their intended access within NR-PEACH.
- JWT tokens will be validated for authenticity and scope compliance on each request.
- The security infrastructure supporting Keycloak is assumed to be robust and regularly maintained.

## Options Considered

- **No Authentication:** Would allow unrestricted access, posing significant security risks and is not suitable for a
  production environment.
- **Custom Authentication Solution:** Could be tailored to specific needs, but would require significant development
  effort, increase security risks, and lack standardization.
- **OIDC Authentication with Keycloak (chosen):** Standardized, secure, widely adopted, leverages existing security
  infrastructure, supports fine-grained access control via scopes.

## Consequences

### Positive

- Standardized, secure authentication mechanism for service accounts.
- Leverages existing government security infrastructure, reducing the risk of custom implementation errors.
- Supports fine-grained access control via scopes, allowing precise management of service account permissions.

### Negative

- Requires proper management of service accounts and scopes to maintain security.
- Relies on the availability and proper configuration of the Keycloak service.
- Requires non-trivial documentation on Keycloak realm process management.
- Potential dependency on Keycloak updates and changes, which may require adjustments in the integration.
